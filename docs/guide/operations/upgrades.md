# Upgrades and troubleshooting

Current `main` source after `v0.1.0-rc.4` uses database schema 4, adding indexes
for federation lookups. Back up the database and encryption key before upgrading.
A schema-3 binary rejects the upgraded schema; use a compatible database backup
when returning to rc.4. Application or Helm rollback does not undo migrations.

Back up the database and matching encryption key first. Review the release notes,
pin the new image version or digest, and run the normal Compose or Helm upgrade.
The migration transaction obtains a PostgreSQL advisory lock. Failed migrations
do not mark the application ready. Existing secret volumes and independently
managed Kubernetes Secrets are never regenerated by an upgrade.

The first version supports one active instance. Helm uses `Recreate`; do not change
it to a rolling multi-replica deployment. Never assume `helm rollback` rolls back
the database. Use a compatible application version or restore a matching database
backup into a new database. The server rejects newer unsupported schemas.

## Development database role check

Before 29 September 2026's Linux acceptance fix, the development Compose/evaluation
chart initialized `grantline` as PostgreSQL's bootstrap superuser. PostgreSQL
rejects demoting that special account. A container restart could subsequently
appear healthy while retaining the excessive database privileges. Fresh installs
now use a separate application owner; replacing a container does not retrofit
roles in an existing volume or PVC.

Check an existing Compose database without changing it:

```sh
docker compose exec postgres psql -U grantline -d grantline -c \
  "SELECT rolname, rolsuper, rolcreatedb, rolcreaterole, rolreplication FROM pg_roles WHERE rolname = current_user;"
```

All four privilege flags must be false. If any are true, preserve a logical
database backup and matching application encryption/setup secrets, initialize a
separate corrected database, then restore and validate there before switching the
application's database connection. Do not delete the old volume, regenerate the
encryption key, or assume an image/Helm upgrade repairs the role. The same check
applies to retained evaluation PVCs. External PostgreSQL installations should
already provide a dedicated non-superuser owner.

## Common checks

| Symptom | Check |
| --- | --- |
| Host/origin rejected | Browser URL and `GRANTLINE_PUBLIC_URL` must match exactly |
| Not ready | Migration result, database reachability, or another active worker |
| MFA code rejected | Time synchronization, correct account, already-used time step |
| SSO unavailable | Issuer discovery, CA, client credentials and exact redirect URI |
| Admin SSO rejected | Provider must assert MFA through the supported claim |
| Source incomplete | Explicit scope, observer permissions, expiry and source availability |
| Imported data appears old | Import preserves collection timestamps; collect a live connection |
| New source settings conflict | Another edit changed its revision; reload before saving |

Check `docker compose logs app migrate` or `kubectl logs` for service status.
Never post secret files, raw tokens, provider response bodies or private reports
to a public issue. Describe the error code and use a sanitized reproduction.

## Uninstall

`docker compose down` removes containers while preserving named volumes.
`helm uninstall` removes the application resources but retains evaluation PVCs and
external Secrets. Deleting volumes, PVCs, external databases or encryption keys is
a separate, destructive operator decision; it is never part of an ordinary upgrade.
